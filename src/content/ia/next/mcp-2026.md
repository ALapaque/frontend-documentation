Le 28 juillet 2026, MCP a publié sa révision la plus lourde depuis l'arrivée des
serveurs distants. Le modèle décrit dans `/ia/senior/mcp` — une connexion, une
poignée de main `initialize`, une session — devient un protocole **requête /
réponse sans état**. Pour un serveur MCP exposé en HTTP, c'est une migration.

## Un cœur sans état

Avant, un serveur HTTP attribuait un `Mcp-Session-Id` après `initialize`, et
chaque requête devait retrouver l'instance qui portait la session : affinité sur
le load balancer, ou stockage partagé. La 2026-07-28 retire `initialize`,
l'en-tête `Mcp-Session-Id`, le flux `GET` permanent et la reprise par
`Last-Event-ID`. À la place, **chaque requête se décrit elle-même** : version du
protocole et capacités du client voyagent dans `_meta`.

```text
POST /mcp HTTP/1.1
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: search_components

{"jsonrpc":"2.0","id":1,"method":"tools/call",
 "params":{"name":"search_components","arguments":{"query":"bouton"},
  "_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28",
           "io.modelcontextprotocol/clientCapabilities":{},
           "io.modelcontextprotocol/clientInfo":{"name":"agent","version":"1.0"}}}}
```

N'importe quelle instance peut répondre, derrière un simple round-robin. Le
serveur doit implémenter `server/discover` (versions, capacités, identité), mais
le client reste libre de s'en passer. Les notifications de changement passent par
un flux unique, `subscriptions/listen`, auquel le client s'abonne type par type.

### L'état applicatif devient un argument

Sans état pour le protocole ne veut pas dire sans état pour ton app. Le serveur
crée un identifiant explicite, un *handle*, et le modèle le repasse en argument.

:::compare
::bad
```ts
// SDK v1 : l'état est accroché à la session de transport.
const paniers = new Map<string, Panier>();
server.registerTool("add_to_cart", { inputSchema: { sku: z.string() } },
  async ({ sku }, extra) => {
    paniers.get(extra.sessionId!)!.add(sku); // quelle instance a la Map ?
    return { content: [{ type: "text", text: "Ajouté." }] };
  },
);
```
::
::good
```ts
// 2026-07-28 : create_cart renvoie un cartId, les autres outils le reçoivent.
server.registerTool(
  "add_to_cart",
  {
    description: "Ajoute un article au panier créé par create_cart.",
    inputSchema: z.object({ cartId: z.string(), sku: z.string() }),
  },
  async ({ cartId, sku }) => {
    await db.carts.add(cartId, sku); // stockage partagé, clé explicite
    return { content: [{ type: "text", text: "Ajouté." }] };
  },
);
```
::
:::

**Pourquoi.** Le handle est visible du modèle, qui le fait circuler d'un outil à
l'autre ; l'état de session, lui, était caché dans le transport. Vérifie quand
même que le handle appartient à l'appelant authentifié : c'est une entrée.

## Côté TypeScript : le SDK v2, en paquets séparés

Les SDK TypeScript, Python, Go et C# parlaient 2026-07-28 le jour de la sortie.
Pour TypeScript, cela désigne la **v2** : `@modelcontextprotocol/server` et
`@modelcontextprotocol/client` (2.4.0 fin novembre 2026). L'ancien paquet
`@modelcontextprotocol/sdk` (1.32.2) est une ligne de maintenance qui s'arrête à
la spec 2025-11-25, corrigée au moins six mois après la sortie de la v2.

```ts
import { createMcpHandler, McpServer } from "@modelcontextprotocol/server";
import * as z from "zod/v4";

const handler = createMcpHandler(() => {
  const server = new McpServer({ name: "design-system", version: "2.0.0" });
  server.registerTool(
    "search_components",
    { description: "Cherche un composant.", inputSchema: z.object({ q: z.string() }) },
    async ({ q }) => ({ content: [{ type: "text", text: await searchDocs(q) }] }),
  );
  return server;
});
export default handler; // Workers, Deno, Bun : rien d'autre à monter
```

**Pourquoi.** `createMcpHandler` reçoit une **fabrique**, appelée à chaque
requête : rien ne survit entre deux appels, donc rien à partager entre instances.
Sous Node, tu enveloppes le handler avec `toNodeHandler` de
`@modelcontextprotocol/node`. Il ne valide ni `Host`, ni `Origin`, ni jeton :
ces contrôles se montent devant lui. La même fabrique sert aussi les clients
restés à l'ère `initialize`. Pour migrer, lance d'abord le codemod officiel :
`npx @modelcontextprotocol/codemod@latest v1-to-v2 .`

## MRTR : poser une question sans flux ouvert

Un outil a parfois besoin de l'utilisateur en cours d'appel : une confirmation,
un paramètre manquant. Avant, le serveur envoyait `elicitation/create` au client
sur un flux maintenu ouvert. Le remplaçant : **Multi Round-Trip Requests**.

1. Le client appelle `tools/call`.
2. Le serveur répond `resultType: "input_required"`, avec une table
   `inputRequests` (clé → demande) et, au besoin, un `requestState` opaque.
3. Le client recueille les réponses puis **rejoue le même appel**, avec un nouvel
   `id`, en ajoutant `inputResponses` (mêmes clés) et le `requestState` reçu.
4. Le serveur termine : `resultType: "complete"`.

```ts
import { acceptedContent, inputRequired } from "@modelcontextprotocol/server";
import type { CallToolResult, InputRequiredResult } from "@modelcontextprotocol/server";

const confirmation = z.object({ confirm: z.boolean() });
server.registerTool(
  "delete_project",
  { description: "Supprime un projet.", inputSchema: z.object({ id: z.string() }) },
  async ({ id }, ctx): Promise<CallToolResult | InputRequiredResult> => {
    const reponse = acceptedContent(ctx.mcpReq.inputResponses, "confirm", confirmation);
    if (reponse?.confirm !== true) {
      const demande = inputRequired.elicit({
        message: `Supprimer le projet ${id} ? Action irréversible.`,
        requestedSchema: confirmation,
      });
      return inputRequired({ inputRequests: { confirm: demande } });
    }
    await projets.supprimer(id); // l'effet de bord en dernier
    return { content: [{ type: "text", text: `Projet ${id} supprimé.` }] };
  },
);
```

**Pourquoi.** Le handler ne pousse plus rien, il **retourne** la demande — et il
est réexécuté **en entier** à chaque tour : lis d'abord les réponses, déclenche
l'effet de bord en dernier. Seuls `tools/call`, `prompts/get` et `resources/read`
peuvent répondre `input_required`. `ctx.mcpReq.elicitInput`, le canal poussé de
2025, lève une erreur sur une requête 2026-07-28.

:::callout{type="warn"}
`inputResponses` et `requestState` reviennent **par le client** : traite-les
comme des entrées hostiles. La spec impose de protéger l'intégrité de
`requestState` (HMAC ou AEAD) dès qu'il influence une autorisation ou la logique
métier ; le SDK fournit `createRequestStateCodec` pour le signer et l'expirer.
:::

**Dépréciés au passage** : Roots, Sampling et Logging. Ne les adopte plus : passe
les chemins en paramètres d'outil, appelle directement l'API de ton fournisseur
de modèle, journalise sur `stderr` ou via OpenTelemetry. L'élicitation reste, via
MRTR. Le transport HTTP+SSE de 2024 est lui aussi classé déprécié.

## Routage et cache : MCP se comporte comme du HTTP

**Des en-têtes obligatoires.** Chaque `POST` porte `Mcp-Method` (la méthode
JSON-RPC) ; `tools/call`, `prompts/get` et `resources/read` y ajoutent `Mcp-Name`
(nom de l'outil ou du prompt, URI de la ressource). Ta passerelle ou ton WAF
routent et mesurent sans parser le corps. Si en-têtes et corps divergent, le
serveur répond `400` avec l'erreur `-32020` (`HeaderMismatch`).

**Des listes cachables.** Les résultats de `server/discover`, des listes
(`tools/list`, `prompts/list`, `resources/list`…) et de `resources/read` portent
deux champs obligatoires : `ttlMs`, fraîcheur dans l'esprit de `Cache-Control:
max-age`, et `cacheScope`, `"public"` ou `"private"`. La spec recommande aussi un
**ordre déterministe** pour `tools/list` : le catalogue part dans le prompt du
modèle, et s'il change d'ordre, le cache de prompt saute (`/ia/medior/ai-sdk`).

Dans le SDK v2, l'option `cacheHints` de `McpServer` règle ces valeurs par
opération : `{ "tools/list": { ttlMs: 300_000, cacheScope: "public" } }`. Sans
elle, le SDK émet `ttlMs: 0` et `cacheScope: "private"` : rien n'est caché. Ne
déclare `"public"` que si la liste est identique pour tous : un cache partagé
peut la resservir à un autre utilisateur, et ce n'est pas un contrôle d'accès.

## Autorisation : trois durcissements, un remplacement

L'autorisation reste de l'OAuth 2.1 (les bases : `/web/senior/auth-sessions-oauth`).

- **Validation de `iss` (RFC 9207).** Le serveur d'autorisation devrait renvoyer
  son identifiant d'émetteur ; le client **doit** le vérifier avant d'échanger le
  code. Cela ferme l'attaque par confusion de serveurs d'autorisation.
- **Identifiants liés à l'émetteur** : ceux obtenus auprès d'un serveur
  d'autorisation ne se réutilisent jamais auprès d'un autre.
- **CIMD à la place de DCR**, déprécié. Avec un *Client ID Metadata Document*
  (encore un draft IETF), le `client_id` est une URL HTTPS où le serveur
  d'autorisation lit un JSON que tu héberges.
- **Enterprise-Managed Authorization**, extension stable : le fournisseur
  d'identité de l'entreprise décide quels serveurs MCP un employé peut utiliser.

## Extensions : ce qui vit hors du cœur

La 2026-07-28 formalise les extensions : un champ `extensions` dans les capacités,
des identifiants `io.modelcontextprotocol/<nom>` et un cycle Experimental → Beta →
Stable (ou promotion dans le cœur).

| Extension | Statut | Rôle |
| --- | --- | --- |
| MCP Apps | Stable | UI interactive rendue dans la conversation |
| Tasks | Bêta, destinée au cœur | Opérations longues (`tasks/get`, `tasks/update`) |
| Events | Bêta | S'abonner à des événements : polling, push ou webhook |
| Skills over MCP | Bêta | Exposer des skills (`SKILL.md`) via les resources |
| Fichiers | Expérimental | Transferts lourds hors du contexte du modèle |

:::callout{type="warn"}
**Statuts à novembre 2026.** Tasks, Events et Skills over MCP sont en **bêta** :
des changements cassants restent possibles. L'extension fichiers est un
**prototype expérimental** qui peut changer ou disparaître. La `2027-03-30` est
une **date cible**, pas une version publiée.
:::

## Calendrier : enfin planifiable

Depuis le 11 novembre 2026, MCP vise **deux révisions par an**, le dernier mardi
de mars et de septembre ; une proposition pas prête glisse à la suivante.
Prochaine cible : le 30 mars 2027, donc `2027-03-30`, avec des bêtas des SDK
Tier 1 un mois et demi avant. La politique de dépréciation garantit **douze mois
minimum** : Roots, Sampling, Logging et DCR ne peuvent être retirés qu'à partir
de la première révision publiée le 28 juillet 2027 ou après — donc pas en mars.

## À retenir

Prépare-toi dans cet ordre : passe au SDK v2, remplace l'état de session par des
handles, convertis les élicitations poussées en `inputRequired`, n'ajoute plus
rien sur Roots, Sampling ou Logging, puis teste les bêtas des SDK dès leur sortie.
